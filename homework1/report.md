## 解題說明

本題要求實作非遞迴（迭代）版本的阿克曼函數（Ackermann's function），計算 $A(m, n)$ 之值。

### 阿克曼函數數學定義

阿克曼函數定義如下：

$$A(m, n) =  \begin{cases}  n + 1 & \text{if } m = 0 \\  A(m - 1, 1) & \text{if } n = 0 \\  A(m - 1, A(m, n - 1)) & \text{otherwise}  \end{cases}$$

### 解題策略

1. 由於阿克曼函數成長速度極快，遞迴呼叫容易造成系統呼叫堆疊（Call Stack）溢位，本實作採用**自訂堆疊（陣列 `nfu`）**模擬遞迴過程：
   - 使用一維陣列 `nfu` 與指標 `top` 來管理堆疊狀態。
   - 初始時將參數 $m$ 推入堆疊中。
2. 透過 `while (top >= 0)` 迴圈模擬遞迴呼叫與返回流程：
   - 當 $cur\_m = 0$ 時：代表達到基底條件，將 $n$ 加 1（`n = n + 1`）。
   - 當 $n = 0$ 時：對應 $A(m-1, 1)$，更新堆疊頂端為 $cur\_m - 1$，並設 $n = 1$。
   - 其餘情況：對應 $A(m-1, A(m, n-1))$，依序將外層任務 $cur\_m - 1$ 與內層任務 $cur\_m$ 推入堆疊，並將 $n$ 減 1（`n = n - 1`）。
3. 當堆疊清空（`top < 0`）時結束迴圈，主程式呼叫函式並輸出計算結果。

## 程式實作

以下為主要程式碼：

```cpp
#include <iostream>
using namespace std;

int data(int m, int n) {
    int nfu[100000]; 
    int top = -1; 
    top++;
    nfu[top] = m;
    while (top >= 0) {
        int cur_m = nfu[top];
        top--;
        if (cur_m == 0) {
            n = n + 1;
        } 
        else if (n == 0) {
            top++;
            nfu[top] = cur_m - 1; 
            n = 1;
        } 
        else {
            top++;
            nfu[top] = cur_m - 1;
            top++;
            nfu[top] = cur_m;  
            n = n - 1;
        }
    }
    return n;
}

int main() {
    int m, n;
    cout << "請輸入 m 和 n: ";
    cin >> m >> n;
    cout << "計算結果 (非遞迴): " << data(m, n) << endl;
    return 0;
}
```


## 效能分析

1. **時間複雜度：** 阿克曼函數為超越指數等級極速成長的函數。對於較小的 $m$ 值：
   - $m = 0: O(1)$
   - $m = 1: O(n)$
   - $m = 2: O(n)$
   - $m = 3: O(2^n)$
   - 一般性表達式為 $O(A(m, n))$，屬於極度爆炸性成長。
2. **空間複雜度：** $O(\text{Max Stack Depth})$。空間開銷取決於執行過程中自訂堆疊 `nfu` 的最大深度，最大開銷與當次運算所需的堆疊深度成正比。

## 申論及開發報告

### 為什麼這題必須用非遞迴？探討它跟遞迴差在哪

這一次作業特別限制一定要用「非遞迴」來寫阿克曼函數（Ackermann's function）。阿克曼函數是個數字爆長極快的超狂函數，拿它來比較「遞迴」跟「非遞迴」的差別，真的超有感！

#### 1. 記憶體管理：系統 Call Stack vs 自訂 Stack

- **遞迴寫法（用系統的 Call Stack）：**  
  如果用一般的遞迴寫，程式每呼叫自己一次，系統就會在 Call Stack 裡面開一塊空間（Stack Frame）來記住現在跑到哪、變數是多少。但系統給的 Call Stack 空間非常小（通常才幾 MB），阿克曼函數又會一口氣鑽超級深，結果數字稍微大一點點，系統堆疊就直接被塞爆，跳出慘絕人寰的 **Stack Overflow** 崩潰。

- **非遞迴寫法（我們自己建的 Stack）：**  
  為了符合作業要求，我們改成用非遞迴，並自己宣告一個陣列 `nfu` 當做 Stack。自己建的 Stack 是放在主記憶體的資料區（Data Segment），空間比系統 Call Stack 大太多了！這樣就算運算鑽得再深，程式也比較能頂得住，不會一下就打回原形。

#### 2. 控制流程：自動配對 vs 手動排隊

- **遞迴寫法：**  
  碰到像 $A(m - 1, A(m, n - 1))$ 這種兩層遞迴時，編譯器跟系統會自動幫你處理好「先算內層、再算外層」的順序。程式碼看起來非常乾淨優雅，跟數學公式長得一模一樣，但底層到底是怎麼轉的你其實看不到。

- **非遞迴寫法：**  
  沒有系統幫忙，我們就得自己手動來。程式裡把 $m - 1$ 跟 $m$ 依序推進 Stack 裡面，其實就是我們手動在指揮：「先拿內層的 $A(m, n-1)$ 出來算，算完結果再丟給外層的 $m-1$」。雖然寫起來比較繁瑣，但能完全掌握整個運算過程。

#### 3. 一張表看懂兩者差別

| 比較項目 | 一般遞迴版 (Recursive) | 本次採用的非遞迴版 (Non-recursive) |
| :--- | :--- | :--- |
| **作業規範** | 不符合規定 | **完全符合這次作業限制** |
| **程式碼好不好讀** | 超好讀（跟數學公式一樣直觀） | 比較繞口（要手動管理 Stack 跟 while 迴圈） |
| **記憶體用哪裡** | 空間超小的系統 Call Stack | 空間大很多的自訂陣列 (Data Segment) |
| **執行效率** | 頻繁進出函式，額外開銷大 | 沒有函式呼叫開銷，狀態轉移比較快 |
| **當機 (Overflow) 風險** | 輸入超小（如 $m=3, n=4$）就直接崩潰 | 空間承受力高很多，但還是受限於陣列 `nfu[100000]` 的大小 |

#### 4. 總結

雖然阿克曼函數用遞迴寫最直覺，但因為作業限制加上系統記憶體的瓶頸，用非遞迴才是比較穩妥的做法。這次實作用陣列模擬 Stack，不僅達成了作業的要求，也讓我們更清楚看到程式底層在處理複雜邏輯時，記憶體到底是怎麼運作的！
